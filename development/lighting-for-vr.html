Part I: Why Lighting Is Different in VR

Constraints That Shape Every Decision

The Fundamental Problem

VR renders the scene twice per frame — once for each eye

Every light, shadow, and post-processing effect costs double compared to flat-screen rendering

Frame Budgets Are Non-Negotiable

Dropped frames cause motion sickness — not just annoyance

Frame time is a better measure than frame rate — it captures consistency

Lighting and Presence

  • Global illumination, ambient occlusion, and shadow quality directly influence how "real" an environment feels
  • Flickering shadows or inconsistent illumination between eyes causes discomfort
  • Too-dark environments break immersion (common when relying on direct light only)

The challenge: achieve high visual quality within extreme performance constraints

Why Forward Rendering for VR?

  • MSAA support — hardware anti-aliasing critical for VR clarity
  • Lower memory — no G-buffer for both eyes
  • Single-Pass Instanced — compatible with forward rendering
  • Mobile-friendly — lower bandwidth, works well on Quest GPUs

Deferred rendering does not support MSAA and has poor single-pass instanced support — avoid for VR

Single-Pass Instanced Rendering

The most performant stereo rendering method

Multi-Pass

  • Renders scene once per eye
  • CPU culls objects twice
  • ~2x draw calls

Single-Pass Instanced

  • GPU instancing renders both eyes in parallel
  • One instanced draw call (count of 2)
  • ~1x draw calls

On Quest, this becomes Multi-View — the graphics driver handles eye multiplexing automatically

Anti-Aliasing in VR

MethodVR SuitabilityNotes

Unity 6.3 Improvements

  • xAtlas lightmap packing — up to 27% memory savings
  • Render Graph Viewer connects to XR device builds for live profiling
  • URP and HDRP now share the same underlying compiler and API

Part IV: Light Baking

Pre-Computing Light for Free Runtime Performance

Why Baking Matters More in VR

  • Baked lighting has zero runtime cost — it's just texture lookups
  • With stereo rendering eating the frame budget, "free" lighting is essential
  • Baked GI produces soft indirect illumination that would be prohibitively expensive in real-time

Unity 6 Lightmapper

  • Progressive GPU Lightmapper (OpenCL) is now the default in 6.3
  • Enlighten baking backend is removed in Unity 6
  • CPU lightmapper still available as fallback

xAtlas: New lightmap packing algorithm generates tighter UV layouts with up to 27% memory savings

Baking Tips for VR

  • Mark static geometry: Contribute GI + Batching Static on all non-moving objects
  • Scale In Lightmap: Reduce texel density on objects players won't inspect closely
  • Small objects: Disable Contribute GI; light them with probes instead
  • Visualize: Scene View → Draw Mode → Baked Lightmap to check texel distribution
  • Always test on device — editor preview can be misleading

Part V: Adaptive Probe Volumes

The New Standard for Dynamic Object Lighting

The Problem with Legacy Light Probes

Light Probe Groups (Legacy)

  • Manually place every probe by hand
  • Time-consuming, error-prone
  • Per-object sampling: one blended value per GameObject
  • Visible seams between adjacent objects

Adaptive Probe Volumes (New)

  • Automatic placement based on geometry
  • Minimal manual setup
  • Per-pixel sampling: 8 nearest probes per pixel
  • Smooth transitions, no seams

How APV Works: Bricks

Unity fills the scene with a 3D grid of bricks

  • Each brick contains 64 light probes in a 4×4×4 arrangement
  • Brick size adapts to geometry density:
Brick SpacingWhere Used
1mDense geometry (furniture, doorways)
3mModerate detail areas
9mOpen interior spaces
27mLarge outdoor areas

Dense where it matters, sparse where it doesn't — automatic LOD for lighting

Per-Pixel vs Per-Object

Legacy: Each GameObject samples a single blended probe value → flat lighting, visible seams between objects

APV: Each pixel samples the 8 closest probes around it → smooth gradients across surfaces, quality approaching lightmaps

This is the single biggest quality improvement for dynamic objects in VR

APV Key Features

  • Lighting Scenarios
    Store day/night states, blend at runtime
  • Sky Occlusion
    Dynamic time-of-day via occlusion data
  • Streaming
    Load/unload probe data for large worlds
  • Baking Sets
    Organize multi-scene baking
  • Probe Adjustment Volumes
    Fix artifacts — dark spots, light leaks
  • Automatic Density
    No manual probe placement needed

Setting Up APV

1 Enable APV: Project Settings → Quality → URP Asset → Lighting → Light Probe System → Adaptive Probe Volumes
2 Add Volume: GameObject → Light → Adaptive Probe Volume → set Mode to Global
3 Configure Lights: Set light Mode to Mixed or Baked
4 Configure Objects: Enable Contribute GI; set Receive GI to Light Probes
5 Bake: Window → Rendering → Lighting → enable Baked GI → Generate Lighting
6 Fine-tune: Add Probe Adjustment Volume components to fix dark spots or light leaks

APV Limitations

  • Cannot manually adjust individual probe positions
  • Cannot convert existing Light Probe Groups to APV
  • Requires baking — not purely real-time
  • May appear vertex-lit on very low-poly geometry — test on device

Part VI: Reflection Probes & Rendering Layers

Environment Reflections and Lighting Control

Reflection Probes

  • Capture a cubemap of surroundings for reflective/metallic materials
  • Each probe has a box-shaped influence volume
  • Maximum 2 probes affect any pixel (blended by distance)
  • Pixels outside all volumes fall back to the skybox

Prefer baked probes for VR — real-time probes re-render the scene into a cubemap, which is very expensive

Rendering Layers (Light Layers)

Control which lights affect which objects

1 Enable: URP Asset → Lighting → Use Rendering Layers
2 Name layers: Project Settings → Tags and Layers → Rendering Layers
3 Assign to lights: Light component → General → Light Layer
4 Assign to objects: Mesh Renderer → Additional Settings → Rendering Layer Mask

Rendering Layers — VR Use Cases

  • Separate character lighting from environment lighting
  • Dramatic lighting that doesn't affect UI elements
  • Custom shadow layers — objects cast shadows from lights that don't illuminate them

Performance tip: keep to a few layers — cost increases at 9, 17, 25+ layers

Part VII: Post-Processing in VR

What to Use, What to Avoid

The Volume System

  • Post-processing uses the Volume component (Global or Local)
  • Global Volume: affects entire scene
  • Local Volume: affects only within its collider bounds

Local volumes are great for rooms with different lighting moods

Post-Processing for VR

EffectVR?Notes
Tonemapping Use Essential for consistent HDR → LDR mapping
Color Adjustments Use Exposure, contrast, saturation
Vignette Careful Can help with comfort tunneling
Bloom Sparingly Can cause discomfort; expensive on Quest
SSAO Avoid Breaks at screen edges; bake AO instead
SSR Avoid Reflections vanish when source leaves screen
Depth of Field Avoid Conflicts with natural eye focus in VR

Why Screen-Space Effects Fail in VR

  • No data beyond the viewport edge — effects flicker as you turn your head
  • Effects render per-eye, doubling cost
  • SSAO/SSR artifacts are amplified because VR fills your peripheral vision

Alternative: Bake ambient occlusion into lightmaps and use Reflection Probes instead of SSR

Part VIII: Quest Optimization

Lighting for Standalone VR

Quest Lighting Rules

  • Baked lighting is mandatory — not optional
  • Maximum 1 real-time directional light (if any)
  • Disable soft shadows — not worth the cost
  • Point lights with real-time shadows are extremely expensive (6 cubemap faces)
  • Use Subtractive mixed lighting mode for best Quest performance

BakedLit vs Lit Materials

BakedLit (URP)

  • Only responds to baked lighting
  • Cheaper shader — fewer calculations
  • Best for static environment objects

Lit (URP)

  • Responds to real-time + baked lighting
  • More expensive shader
  • Needed for objects affected by dynamic lights

Use BakedLit for maximum performance on purely baked objects

Part IX: Putting It All Together

A Practical VR Lighting Workflow

VR Lighting Workflow

1 Pipeline: URP, Forward rendering, Single-Pass Instanced (or Multi-View on Quest)
2 Set all lights to Baked initially — optimize first, add dynamics later
3 Mark static geometry: Contribute GI + Batching Static on all non-moving objects
4 Enable APV: Add a Global Adaptive Probe Volume for dynamic object lighting
5 Bake at low quality (resolution 5–10), test on device, iterate

VR Lighting Workflow (cont.)

6 Add dynamics sparingly: At most one Mixed directional for player shadows
7 Use fake techniques for dynamic effects: blob shadows, emissives, light cookies
8 Raise lightmap quality for final build (resolution 20–80)
9 Profile on device: Unity Profiler + Render Graph Viewer (new in 6.3)
10 Fix artifacts: Probe Adjustment Volumes, lightmap visualization, shadow tuning

Common Mistakes & Fixes

ProblemCauseFix
Too-dark scenes No indirect lighting Increase Indirect Intensity; use ambient/environment light
Flickering shadows Low shadow map resolution Reduce Max Shadow Distance; increase resolution
Z-fighting shimmer Coplanar geometry Offset surfaces slightly; increase depth precision
Specular aliasing Sharp highlights + head movement Reduce smoothness on detailed meshes; use MSAA
APV dark spots Probes inside geometry Add Probe Adjustment Volume to invalidate probes

VR Lighting Checklist

  • 1 URP + Forward rendering + MSAA 4x
  • 2 Single-Pass Instanced (desktop) / Multi-View (Quest)
  • 3 Bake as much lighting as possible
  • 4 Use APV instead of manual Light Probe Groups
  • 5 Max 1 real-time directional for shadows
  • 6 Disable SSAO, SSR, TAA — prefer baked AO + reflection probes
  • 7 Use Rendering Layers to limit light–object interactions
  • 8 Profile on device with Render Graph Viewer
