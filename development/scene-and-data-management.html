Scene & Data Management

Organizing VR Applications

CPSC 4110/6110

Part I: Why Scenes Matter

Beyond a Single Scene

The Scenario

Your VR app needs:

  • A lobby — where the user starts
  • A gameplay environment — the main experience
  • A settings menu — comfort options, controls
  • Multiple levels — different worlds to explore

How do you organize all of this?

What Is a Scene?

  • A container for GameObjects
  • Think of it like a level or environment
  • Saved as a .unity file
  • Has its own hierarchy, lighting, navigation

Scene Contains

MyScene.unity
├── Main Camera
├── Directional Light
├── Terrain
├── Player
│   └── PlayerScript
└── UI Canvas

The "One Giant Scene" Problem

Load Times

Everything loads at once — long startup

Memory

All assets in RAM — critical in VR

Git Conflicts

Everyone editing one scene file

Organization

Hundreds of objects, impossible to navigate

Why VR Makes This Worse

  • 90 FPS minimum — can't afford frame drops during loading
  • Comfort matters — a loading freeze causes discomfort
  • XR Rig must persist — losing head tracking = instant nausea
  • Memory constrained — Quest has ~6 GB usable RAM

A single frame hitch in VR is much worse than on a monitor

Two Approaches

Single Load

Destroy current scene, load a new one

Simple but destructive

Additive Loading

Layer scenes on top of each other

Recommended for VR

Part II: Scene Loading Basics

Loading and Unloading Scenes

Build Settings

Before you can load a scene, Unity needs to know about it.

File → Build Settings → Scenes In Build

  ✓ Scenes/Lobby          (index 0)
  ✓ Scenes/Gameplay       (index 1)
  ✓ Scenes/Settings       (index 2)

Only scenes listed here can be loaded at runtime

Simple Scene Loading

using UnityEngine.SceneManagement;

public class SceneLoader : MonoBehaviour {
    public void LoadByName() {
        SceneManager.LoadScene("Gameplay");
    }
    public void LoadByIndex() {
        SceneManager.LoadScene(1);
    }
}

Load by scene name or build index from Build Settings

What Happens on LoadScene?

  1. Current scene is destroyed — all GameObjects gone
  2. New scene loads synchronously — game freezes
  3. New scene's Awake/Start run

Problem: Your XR Rig, your score, your game state — all destroyed!

The Synchronous Problem

Desktop

Screen freezes for a moment

Annoying but tolerable

VR

Head tracking stops responding

Nausea-inducing

We need a better approach for VR...

Part III: Additive Loading

The VR-Friendly Approach

Additive vs. Single

Single (Default)

// Destroys everything, loads fresh
SceneManager.LoadScene("Level2");

Replace the world

Additive

// Loads ON TOP of current scene
SceneManager.LoadScene("Level2",
    LoadSceneMode.Additive);

Layer scenes together

The VR Scene Pattern

Core Scene (always loaded)
  ├── XR Rig        ├── AudioManager
  ├── GameManager    └── Event System
─────────────────────────────────────
Environment Scene (swappable)
  ├── Terrain / Room   ├── Props
  └── Lighting
─────────────────────────────────────
UI Scene (optional, additive)
  ├── Menus   └── HUD Elements

Swapping Environments

public class LevelManager : MonoBehaviour {
    private string currentLevel;
    public void LoadLevel(string levelName) {
        if (currentLevel != null)
            SceneManager.UnloadSceneAsync(currentLevel);
        SceneManager.LoadSceneAsync(levelName, LoadSceneMode.Additive);
        currentLevel = levelName;
    }
}

Async Loading

LoadSceneAsync loads in the background over multiple frames

IEnumerator LoadLevelAsync(string levelName) {
    AsyncOperation op = SceneManager.LoadSceneAsync(
        levelName, LoadSceneMode.Additive);

    while (!op.isDone) {
        float progress = op.progress;  // 0.0 to 1.0
        // Update loading bar, fade screen, etc.
        yield return null;
    }
    Debug.Log("Level loaded!");
}

Why Async Matters for VR

Head Tracking

Continues during load

No Freeze

Loading spread across frames

Loading UX

Show progress, fade to black

Comfort

User stays oriented

Rule of thumb: Always use LoadSceneAsync in VR

Transition Strategy

  1. Fade to black (or a loading environment)
  2. Start async load of new scene
  3. Unload old scene async
  4. Wait for both operations
  5. Fade back in

The user never sees a "loading screen" — just a brief fade

Part IV: Keeping Data Alive

Persistence Across Scenes

The Problem

When a scene is unloaded, its GameObjects are destroyed.

Player score? Gone.
Settings? Gone.
Game state? Gone.

How do we keep data alive across scene transitions?

Three Approaches

DontDestroyOnLoad

Keep a GameObject alive forever

ScriptableObjects

Data assets in your Project

Static Classes

Pure C# — no MonoBehaviour

Approach 1: DontDestroyOnLoad

public class GameManager : MonoBehaviour {
    public static GameManager Instance;
    public int score;

    void Awake() {
        if (Instance == null) {
            Instance = this;
            DontDestroyOnLoad(gameObject);
        } else Destroy(gameObject);  // Only one!
    }
}

The "Singleton" pattern — one instance survives all scene loads

Using the Singleton

// From ANY script, in ANY scene:
GameManager.Instance.score += 100;

// Check current level
if (GameManager.Instance.currentLevel == "Boss")
    ShowWarning();

VR use case: Your XR Rig lives in a DontDestroyOnLoad scene — it persists as you load new environments

Approach 2: ScriptableObjects

[CreateAssetMenu(menuName = "Data/Player Data")]
public class PlayerData : ScriptableObject {
    public int score;
    public int health;
    public float snapTurnAngle;
    public float vignetteIntensity;
}

Create in Project: Right-click → Create → Data → Player Data

Lives in your Project, not in any scene

ScriptableObjects: Shared Data

Scene A:

public class ScoreDisplay : MonoBehaviour {
    public PlayerData playerData;
    void Update() {
        text.text = "Score: " + playerData.score;
    }
}

Scene B:

public class Enemy : MonoBehaviour {
    public PlayerData playerData;  // Same asset!
    void OnDestroy() {
        playerData.score += 50;
    }
}

Both reference the same asset — changes are shared automatically

Approach 3: Static Classes

public static class GameState {
    public static int score;
    public static string playerName;
    public static float comfortLevel;
}
// Use from anywhere:
GameState.score += 100;

Simple, but no Inspector support, hard to test, and can become a dumping ground

Comparison

Feature DontDestroy ScriptableObject Static
Inspector editing
MonoBehaviour features
Scene independent
Survives Play Mode
Multiple instances Singleton only Many assets One global

When to Use What

DontDestroyOnLoad

  • XR Rig
  • Audio Manager
  • Network Manager

Needs to run code every frame

ScriptableObjects

  • Player stats
  • Comfort settings
  • Inventory data

Pure data, shared across scenes

Static Classes

  • Constants
  • Utility functions
  • Quick prototyping

Simple, no frills

Part V: ScriptableObjects

Data That Lives Outside Scenes

What Are ScriptableObjects?

  • Data containers saved as assets in your Project
  • Don't attach to GameObjects
  • Don't live in any scene
  • Editable in the Inspector
  • Persist between scenes (and between Play sessions in Editor)

Creating a ScriptableObject

[CreateAssetMenu(menuName = "VR/Comfort Settings")]
public class ComfortSettings : ScriptableObject {
    [Header("Locomotion")]
    public float snapTurnAngle = 30f;
    public bool smoothLocomotion = false;
    public float moveSpeed = 2f;
    [Header("Comfort")]
    [Range(0, 1)] public float vignetteIntensity = 0.5f;
    public bool showFloor = true;
}

Using It

public class LocomotionController : MonoBehaviour {
    [SerializeField] private ComfortSettings settings;

    void Update() {
        if (settings.smoothLocomotion)
            SmoothMove(settings.moveSpeed);
        else
            SnapTurn(settings.snapTurnAngle);
        vignette.intensity = settings.vignetteIntensity;
    }
}

Any script in any scene can reference the same settings asset

Why This Is Powerful

Shared Reference

Settings menu and locomotion system read the same data

Designer-Friendly

Tweak values in Inspector, no code changes

Multiple Presets

Create "Comfortable", "Moderate", "Intense" presets

No Scene Dependency

Data survives scene transitions automatically

ScriptableObjects as Events

Problem: How do objects in different scenes communicate without direct references?

GameEvent.cs (ScriptableObject)

[CreateAssetMenu(menuName = "Events/Game Event")]
public class GameEvent : ScriptableObject {
    private List<GameEventListener> listeners = new();
    public void Raise() {
        foreach (var l in listeners)
            l.OnEventRaised();
    }
    public void Register(GameEventListener l)
        => listeners.Add(l);
    public void Unregister(GameEventListener l)
        => listeners.Remove(l);
}

GameEventListener.cs (MonoBehaviour)

public class GameEventListener : MonoBehaviour {
    public GameEvent gameEvent;
    public UnityEvent response;
    void OnEnable()
        => gameEvent.Register(this);
    void OnDisable()
        => gameEvent.Unregister(this);
    public void OnEventRaised()
        => response.Invoke();
}

How the Event Pattern Works

  1. Create a GameEvent asset in your Project (e.g., "OnLevelComplete")
  2. Any script can Raise the event: onLevelComplete.Raise();
  3. GameEventListener components on GameObjects subscribe automatically
  4. Wire up responses in the Inspector via UnityEvent — no code needed

VR example: An enemy in the Environment scene raises "OnEnemyDefeated" — the score UI in a different scene responds, with no direct reference between them

Part VI: Saving Data

Beyond Runtime Persistence

When Do You Need Save/Load?

  • User preferences — comfort settings that persist between app launches
  • Progress — which levels are unlocked
  • State — saving a game to resume later

DontDestroyOnLoad and ScriptableObjects only persist during a session

PlayerPrefs

Simple key-value storage — good for settings

Save:

PlayerPrefs.SetFloat("SnapTurnAngle", 45f);
PlayerPrefs.SetInt("SmoothLocomotion", 1);
PlayerPrefs.SetString("PlayerName", "Alex");
PlayerPrefs.Save();

Load:

float angle = PlayerPrefs.GetFloat("SnapTurnAngle", 30f);
int smooth  = PlayerPrefs.GetInt("SmoothLocomotion", 0);
string name = PlayerPrefs.GetString("PlayerName", "Player");

Don't store game state here — just simple preferences

JSON Serialization

Data class:

[System.Serializable]
public class SaveData {
    public int score;
    public string currentLevel;
    public float[] playerPosition;
}

Save & Load:

// Save
var data = new SaveData { score = 500 };
string json = JsonUtility.ToJson(data);
File.WriteAllText(path, json);
// Load
string json = File.ReadAllText(path);
var save = JsonUtility.FromJson<SaveData>(json);

Save/Load Summary

MethodBest ForComplexity
PlayerPrefs Settings, preferences Simple
JsonUtility Game state, progress Moderate
Binary / SQLite Large datasets, security Advanced

For this course, PlayerPrefs and JSON cover most needs

Part VII: VR Architecture

Putting It All Together

Recommended VR Project Structure

Persistent Core Scene
XR Rig • GameManager • AudioManager • EventSystem
↓ additive load / unload ↓
Environment Scenes (swappable)
Lobby • Level 1 • Level 2 • ...
↓ references ↓
ScriptableObject Assets
ComfortSettings • PlayerData • GameEvents

How It Fits Together

  1. App starts → Core scene loads (XR Rig, managers)
  2. Core scene additively loads Lobby
  3. User picks a level → fade out
  4. Unload Lobby async, load Level 1 async
  5. Fade in — XR Rig never moved
  6. ScriptableObjects hold data throughout
  7. On quit → save preferences with PlayerPrefs

File Organization

Assets/
├── Scenes/
│   ├── Core.unity       ← Persistent
│   ├── Lobby.unity      ← Additive
│   ├── Level_01.unity   ← Additive
│   └── Level_02.unity   ← Additive
├── Data/
│   ├── ComfortSettings.asset
│   ├── PlayerData.asset
│   └── Events/
├── Scripts/
│   ├── Managers/
│   └── Data/

Tips for Success

  • Always use async loading in VR — never freeze the frame
  • Keep your XR Rig in one persistent scene
  • Use ScriptableObjects for shared data — not static globals
  • Fade to black during transitions — respect user comfort
  • Test on device — loading performance differs from Editor
  • Keep scenes focused — one responsibility per scene
