The Core Insight for VR

Animation in VR splits into two fundamentally different problems:

NPC Animation

Works like any flatscreen game — Animator Controllers, Blend Trees, state machines, root motion

Player Avatar Animation

Driven by hardware tracking via IK — no traditional state machine, no root motion

Keep this split in mind as we learn each tool — it determines where each technique applies

Part II: Animation Clips

The Atomic Unit of Motion

What Is an Animation Clip?

A single piece of recorded motion — one jump, one walk cycle, one wave

Clips are the fundamental building blocks that the Animator Controller orchestrates

What's Inside a Clip?

  • Animation Curves — each records how one property changes over time (position, rotation, blend shape weight, material color, ...)
  • Keyframes — data points on each curve, with tangent handles controlling interpolation
  • Animation Events — markers that call C# methods at specific times

Dopesheet vs Curves View

Dopesheet

Shows keyframes as diamonds on a timeline

Best for adjusting timing — when things happen

Curves

Shows interpolation curves with editable Bézier handles

Best for fine-tuning easing and motion quality

Key Import Settings: Loop

  • Loop Time: Enable for anything that repeats (idle, walk, run)
  • Loop Pose: Smoothly blends the gap between last and first frame
  • Unity shows green/yellow/red indicators for loop quality

Green = seamless loop. Aim for green on all looping clips.

Root Transform Settings

SettingBake Into Pose ONBake Into Pose OFF
Rotation No rotation from clip Clip drives rotation
Position Y No vertical movement (good for walks) Height changes apply (needed for jumps)
Position XZ No horizontal drift (good for idles) Animation drives horizontal (root motion)

Typical walk cycle: Rotation ON, Y ON, XZ OFF (if using root motion)

Editing Imported Clips

Clips inside FBX containers are read-only

To edit: select the clip → press Ctrl+D to duplicate as a standalone .anim asset

Then open in Window → Animation → Animation to modify keyframes, add events, adjust curves

Part III: The Animator Controller

A Visual State Machine for Animations

The Brain of the Animation System

An Animator Controller is a visual state machine that determines:

  • Which animation plays
  • When transitions occur
  • How animations blend together

Create via: Right-click in Project → Create → Animator Controller

Core Node Types

Entry
Default State
Regular State
Any State
Exit
  • States (grey) — each plays one Clip or Blend Tree
  • Default State (orange) — first state entered on activation
  • Any State (teal) — transitions from here apply universally (interrupts)
  • Entry (green) / Exit (red) — state machine boundaries

Transitions

Right-click a state → Make Transition → click the destination

  • Has Exit Time: Should the transition wait for the clip to reach a point?
  • Exit Time: Normalized point in source clip (0–1) when transition can begin
  • Transition Duration: How long the crossfade takes
  • Conditions: Parameter-based rules that must ALL be true

Rule of thumb: Disable Has Exit Time for responsive gameplay (idle→walk on input). Enable it for animations that must complete (attack→idle).

Parameters: Four Types

TypeWhen to useExample
Float Continuous values; driving Blend Trees Speed, Direction
Bool Persistent binary states IsGrounded, IsAlive
Int Discrete numbered states WeaponType, ComboIndex
Trigger One-shot events; auto-resets Jump, Attack

Trigger vs Bool

Trigger

Instantaneous action; auto-resets after one transition consumes it

Use for: Jump, Attack, Die

Bool

Persists until explicitly changed

Use for: IsGrounded, IsCrouched, IsAlive

Demo: Idle → Walk → Run

1 Create Animator Controller, add Float parameter Speed
2 Drag Idle, Walking, Running clips into the Animator window
3 Set Idle as default, create transitions between all three states
4 Add conditions: Idle→Walk (Speed > 0.1), Walk→Run (Speed > 3), etc.
5 Disable Has Exit Time on all transitions; set Duration to ~0.15s

Interlude: The Input System

Before we script the Animator, we need to read input. We'll use Unity's new Input System (UnityEngine.InputSystem) — not the legacy UnityEngine.Input class.

  • Default for all new XR projects
  • Supports keyboard, gamepad, XR controllers, touch with a unified API
  • Rebindable at runtime
  • All scripts in this deck assume you're using it

Creating an Input Actions Asset

1 Window → Package Manager → install Input System (restart if prompted)
2 Right-click Project → Create → Input Actions → name it PlayerInputActions
3 Double-click to open the editor; add an Action Map named Player
4 Add actions: Move (Vector2, WASD composite), Sprint (Button, Left Shift), Jump (Button, Space), Wave (Button, G)
5 Click Save Asset — the asset won't update until you do!

Diagonal Normalization Gotcha

WASD composites default to Digital mode — W+D produces (1, 1), magnitude ~1.41

Diagonal movement is ~41% faster than cardinal movement!

Fix: Select the WASD composite → change Mode from Digital to DigitalNormalized

All scripts in this deck assume normalized input

Driving From Script

using UnityEngine;
using UnityEngine.InputSystem;

[RequireComponent(typeof(Animator))]
public class SimpleLocomotion : MonoBehaviour
{
    public InputActionReference moveAction;

    private Animator animator;
    private static readonly int SpeedHash = Animator.StringToHash("Speed");

    void Awake() => animator = GetComponent<Animator>();
    void OnEnable() => moveAction.action.Enable();
    void OnDisable() => moveAction.action.Disable();

    void Update()
    {
        Vector2 input = moveAction.action.ReadValue<Vector2>();
        Vector3 inputDir = new Vector3(input.x, 0, input.y);
        float speed = inputDir.magnitude * 6f;

        // Damped update: smooths over 0.1s
        animator.SetFloat(SpeedHash, speed, 0.1f, Time.deltaTime);
    }
}

Wire up: expand PlayerInputActions in Project, drag Player/Move into the Move Action field

Key Input System Patterns

  • InputActionReference field — assigned in the Inspector
  • OnEnable() / OnDisable() — always enable and disable actions with the MonoBehaviour
  • .action.ReadValue<Vector2>() — continuous values (movement axes)
  • .action.ReadValue<float>() > 0.5f — button held state
  • .action.WasPressedThisFrame() — one-shot button presses (jump, wave)
  • .action.WasReleasedThisFrame() — button release events

Part IV: Blend Trees

Smooth Locomotion Without Transition Spaghetti

The Problem With Transitions

  • Idle → Walk → Run needs 4 transitions with conditions
  • Add directional movement and the count multiplies exponentially
  • Tuning transition timings becomes a nightmare

Blend Trees continuously interpolate between clips based on parameter values — all within a single state

1D Blend Tree

Blend along a single float parameter (e.g., Speed)

MotionThreshold
Idle0
Walk3
Run6
  • Speed = 0 → 100% Idle
  • Speed = 1.5 → 50% Idle + 50% Walk
  • Speed = 6 → 100% Run

2D Blend Trees

For directional movement (needs two parameters)

  • 2D Simple Directional — one motion per direction; simple 8-way movement
  • 2D Freeform Directional — multiple motions per direction; best for locomotion
  • 2D Freeform Cartesian — parameters unrelated (e.g., speed + turn angle)

Demo: 2D Directional Blend Tree Setup

A full 8-directional locomotion system with walk and run speeds

1 Add two Float parameters: VelocityX (lateral) and VelocityZ (forward/back)
2 Create Blend Tree state → set Blend Type to 2D Freeform Directional
3 Set Parameter X = VelocityX, Parameter Y = VelocityZ
4 Add motion fields with X/Y positions (see next slide)

2D Blend Tree Motion Positions

MotionPos XPos YNotes
Idle00Center — required for Freeform Directional
Walking00.5Forward walk
Running01.0Forward run
Walking Backwards0-0.5Backward walk
Running Backward0-1.0Backward run
Left Strafe Walking-0.50Strafe walk left
Left Strafe-1.00Strafe run left
Right Strafe Walking0.50Strafe walk right
Right Strafe1.00Strafe run right

Inner ring (±0.5) = walk speed, outer ring (±1.0) = run speed

Inspector Preview

  • The Inspector shows a 2D preview diagram with blue dots at each motion's position
  • A red diamond represents the current parameter values
  • Dragging it shows which motions are blending and at what weights

Tip: Start with just Idle, Walk Forward, and Run Forward. The Blend Tree handles missing directions gracefully — add strafe and backward motions later.

Driving the 2D Blend Tree: Setup

using UnityEngine;
using UnityEngine.InputSystem;

[RequireComponent(typeof(Animator), typeof(CharacterController))]
public class DirectionalLocomotion : MonoBehaviour
{
    [Header("Input")]
    public InputActionReference moveAction;
    public InputActionReference sprintAction;

    [Header("Movement")]
    public float walkSpeed = 3f;
    public float runSpeed = 6f;
    public float turnSpeed = 120f; // degrees per second

    private Animator animator;
    private CharacterController controller;
    private static readonly int VxHash = Animator.StringToHash("VelocityX");
    private static readonly int VzHash = Animator.StringToHash("VelocityZ");

    void Awake()
    {
        animator = GetComponent<Animator>();
        controller = GetComponent<CharacterController>();
    }

    void OnEnable()  { moveAction.action.Enable();  sprintAction.action.Enable();  }
    void OnDisable() { moveAction.action.Disable(); sprintAction.action.Disable(); }
}

Update(): Animation Parameters

void Update()
{
    Vector2 input = moveAction.action.ReadValue<Vector2>();
    bool sprinting = sprintAction.action.ReadValue<float>() > 0.5f;

    // --- Animation ---
    // Scale input: 0–0.5 = walk range, 0.5–1.0 = run range
    float speedMultiplier = sprinting ? 1.0f : 0.5f;
    float targetX = input.x * speedMultiplier;
    float targetZ = input.y * speedMultiplier;

    animator.SetFloat(VelocityXHash, targetX, 0.1f, Time.deltaTime);
    animator.SetFloat(VelocityZHash, targetZ, 0.1f, Time.deltaTime);

    // ... movement and rotation next
}

Update(): Movement & Rotation

    // --- Movement: relative to character's facing ---
    float currentSpeed = sprinting ? runSpeed : walkSpeed;
    Vector3 move = (transform.forward * input.y +
                    transform.right   * input.x) * currentSpeed;

    // Gravity
    if (controller.isGrounded) move.y = -0.5f;
    else                       move.y += Physics.gravity.y * Time.deltaTime;

    controller.Move(move * Time.deltaTime);

    // --- Rotation: Q/E to turn (strafing with A/D) ---
    float turnInput = 0f;
    if (Keyboard.current != null)
    {
        if (Keyboard.current.qKey.isPressed) turnInput = -1f;
        if (Keyboard.current.eKey.isPressed) turnInput = 1f;
    }
    transform.Rotate(0f, turnInput * turnSpeed * Time.deltaTime, 0f);
}

Wire Player/Move and Player/Sprint into the Inspector fields

Why Strafing (Not Auto-Facing)?

Auto-Face Movement

Third-person action game style

Character always turns to face where it's going — the 2D blend tree mostly stays near the forward axis

Independent Facing This demo

Shooter / tactical style

Character can strafe sideways and backwards while keeping its facing — the whole 2D blend tree gets exercised

With independent facing, all 9 clips in your blend tree actually get used

How the Mapping Works

  • WASD → move relative to facing (W forward, A/D strafe, S back)
  • Q / E → turn left / right
  • Sprint off: input values land in ±0.5 → walk zone
  • Sprint on (Shift): values reach ±1.0 → run zone
  • Diagonal input (W+D) blends forward and right-strafe motions automatically

1D vs 2D: When to Use Each

ScenarioUse
Character faces movement direction (third-person action) 1D on Speed — direction handled by rotating the model
Character can strafe independently of facing (shooter, VR NPC) 2D on VelocityX / VelocityZ
Forward-only movement at varying speeds 1D on Speed
Directional attack stances or aim blending 2D on aim direction parameters

Why Blend Trees Win

State Machine Many transitions

  • 4+ transitions for 3 states
  • Conditions per transition
  • Discrete hops between animations
  • Exit time tuning needed

Blend Tree Single state

  • Zero transitions
  • One parameter drives everything
  • Continuous smooth blending
  • No exit time needed

Blend Trees are almost always preferred over discrete transitions for locomotion

Part V: Layers & Avatar Masks

Animating Different Body Parts Independently

Why Layers?

Layers let you play different animations on different body parts simultaneously

Example: Character walks (lower body) while waving (upper body) at the same time

Layer Settings

  • Weight (0–1): How strongly this layer affects the final pose
  • Mask: An Avatar Mask restricting which bones this layer controls
  • Blending: Override (replaces) or Additive (adds delta)
  • IK Pass: Enables OnAnimatorIK() for this layer

Avatar Masks

Define which bones a layer can control

1 Right-click Project → Create → Avatar Mask
2 In the Humanoid body diagram, click body parts to toggle included / excluded
3 For upper-body mask: include head, arms, torso; exclude legs and root
4 Assign to your layer via the gear icon → Mask field

Override vs Additive Blending

Override

Layer animation replaces the underlying result for masked bones

Use for: full wave animation on top of walking legs

Additive

Layer animation is treated as a delta from a reference pose and added on top

Use for: breathing, head bob, weapon recoil

Demo: Waving While Walking

1 Base Layer: locomotion Blend Tree (from Part IV)
2 Add Layer UpperBody; Blending = Override; Mask = UpperBodyMask; Weight = 1.0
3 Create Empty default state + Wave state in the new layer
4 Add Bool parameter IsWaving; transitions between Empty ↔ Wave
5 Drive with animator.SetBool("IsWaving", true) on input

Wave Controller Script

using UnityEngine;
using UnityEngine.InputSystem;

[RequireComponent(typeof(Animator))]
public class WaveController : MonoBehaviour
{
    public InputActionReference waveAction;
    private Animator animator;
    private static readonly int IsWavingHash = Animator.StringToHash("IsWaving");

    void Awake()    => animator = GetComponent<Animator>();
    void OnEnable() => waveAction.action.Enable();
    void OnDisable()=> waveAction.action.Disable();

    void Update()
    {
        if (waveAction.action.WasPressedThisFrame())
            animator.SetBool(IsWavingHash, true);
        if (waveAction.action.WasReleasedThisFrame())
            animator.SetBool(IsWavingHash, false);
    }
}

Wire Player/Wave into the Wave Action field. Note: WasPressedThisFrame fires once on the transition from released → held.

Part VI: Root Motion

Should Animation Drive Movement?

What Is Root Motion?

  • During a walk animation, the character's hips (the root bone) translate forward
  • Unity captures this as Root Transform data, separate from the body pose
  • When Apply Root Motion is enabled, this translation drives the GameObject's Transform

Result: Character moves at exactly the speed and cadence of the animation — zero foot sliding

The Apply Root Motion Checkbox

  • ☑ On — root motion from clips drives the GameObject
  • ☐ Off — root motion is discarded; movement is script-controlled
  • "Handled by Script" — shown when you implement OnAnimatorMove()

Custom Handling: OnAnimatorMove()

void OnAnimatorMove()
{
    // Apply root motion to a Rigidbody with gravity preserved
    Rigidbody rb = GetComponent<Rigidbody>();
    Vector3 velocity = animator.deltaPosition / Time.deltaTime;
    velocity.y = rb.velocity.y; // Preserve gravity
    rb.velocity = velocity;
    rb.MoveRotation(rb.rotation * animator.deltaRotation);
}

Lets you scale, redirect, or apply root motion to any movement system

Root Motion vs Script-Driven

FactorRoot MotionScript-Driven
Foot sliding ✓ Eliminated Possible if mismatch
Control Animator drives cadence Programmer drives speed
Responsiveness Can feel sluggish Immediately responsive
VR player × Never ✓ Required
NPCs ✓ Excellent Works fine

Why Root Motion Fails for VR Players

Root motion must never drive the VR player's position

  • The player's position is determined by the HMD's real-world tracking
  • Any discrepancy between physical and virtual position causes motion sickness
  • VR player movement uses XRI Locomotion Providers (continuous move, teleportation)

Root motion is still fine for NPCs in VR — NavMeshAgent + root motion is a standard pattern

Part VII: Animation Events & Scripting

Bridging Animation and Gameplay Logic

Animation Events

Markers at specific frames that invoke C# methods during playback

  • Footstep sounds at foot-contact frames
  • Particle effects during an attack swing
  • Gameplay logic at the apex of a jump
  • Hitbox activation during a combat move

Adding Events in the Editor

1 Open Window → Animation → Animation with the clip selected
2 Scrub to the desired frame
3 Click the Add Event pin icon above the timeline
4 Specify the Function name + optional parameter (float, int, string, or Object)

Event Receiver Script

public class AnimationEventReceiver : MonoBehaviour
{
    public AudioClip footstepClip;
    private AudioSource audioSource;

    void Awake() => audioSource = GetComponent<AudioSource>();

    // Called by animation event at foot-contact frames
    public void PlayFootstep()
    {
        audioSource.PlayOneShot(footstepClip);
    }

    // With a string parameter
    public void OnAttackPhase(string phase)
    {
        Debug.Log($"Attack entered phase: {phase}");
    }
}

The function must be public on a MonoBehaviour on the same GameObject as the Animator

Animator API: Setting Parameters

Animator animator = GetComponent<Animator>();

// Instant set
animator.SetFloat("Speed", 5.0f);

// Damped (smooths value over 0.1s)
animator.SetFloat("Speed", 5.0f, 0.1f, Time.deltaTime);

animator.SetBool("IsGrounded", true);
animator.SetInteger("WeaponType", 2);

// Triggers auto-reset after being consumed
animator.SetTrigger("Jump");
animator.ResetTrigger("Jump"); // manually reset if needed

Animator API: Querying & Direct Control

// Querying current state
AnimatorStateInfo info = animator.GetCurrentAnimatorStateInfo(0); // layer 0
if (info.IsName("Jump"))
    Debug.Log("Currently in Jump state");

float progress = info.normalizedTime; // 0.0–1.0 per loop

// Direct playback control
animator.Play("Run");                        // instant switch

Part VIII: Inverse Kinematics

Procedurally Adjusting Character Poses

What Is IK?

IK lets you procedurally adjust a character's pose at runtime so that hands reach targets, feet plant on uneven terrain, and eyes track objects — without pre-authored animation for every scenario

Forward Kinematics vs Inverse Kinematics

Forward Kinematics

Input: joint rotations (shoulder, elbow)

Output: hand position

"Rotate the shoulder 30°, then the elbow 45°"

Inverse Kinematics

Input: desired hand position

"Put the hand on this doorknob"

Output: joint rotations that get you there

Unity's Built-In Animator IK

For Humanoid rigs, Mecanim provides four end-effector goals plus a LookAt target:

Hands

Left Hand, Right Hand

Feet

Left Foot, Right Foot

LookAt

Head + eye orientation

IK Prerequisites

  • Character must use a Humanoid Avatar
  • Animator Controller layer must have IK Pass enabled (gear icon)
  • A script implementing OnAnimatorIK() must be on the same GameObject

IK Script Example

void OnAnimatorIK(int layerIndex)
{
    // Look At IK — head and eyes track the target
    animator.SetLookAtWeight(1f, 0.3f, 0.6f, 1f, 0.5f);
    // (weight, bodyWeight, headWeight, eyesWeight, clampWeight)
    animator.SetLookAtPosition(lookTarget.position);

    // Right Hand IK — hand reaches for target
    animator.SetIKPositionWeight(AvatarIKGoal.RightHand, 1f);
    animator.SetIKRotationWeight(AvatarIKGoal.RightHand, 1f);
    animator.SetIKPosition(AvatarIKGoal.RightHand, handTarget.position);
    animator.SetIKRotation(AvatarIKGoal.RightHand, handTarget.rotation);
}

IK Execution Order

Animation Evaluation
→
OnAnimatorMove()
→
OnAnimatorIK()
→
Rendering

IK runs after root motion but before the frame is drawn — so IK adjustments override the animation pose

Weight Blending

  • SetIKPositionWeight(goal, 0) → pure animation pose
  • SetIKPositionWeight(goal, 1) → fully IK-driven
  • SetIKPositionWeight(goal, 0.5) → halfway blend

Blend IK weight in/out smoothly to avoid snapping — e.g., as the hand approaches a reachable target, ramp the weight from 0 to 1

Part IX: VR-Specific Considerations

Where Everything We've Learned Splits in Two

The Fundamental Split

NPC Animation

  • Animator Controllers
  • Blend Trees & state machines
  • Root motion OK
  • NavMeshAgent pathfinding

Works just like flatscreen games

Player Avatar

  • IK from headset + controllers
  • No traditional state machine
  • Never root motion
  • XRI Locomotion Providers

Fundamentally different problem

NPC Animation in VR

Exactly like flatscreen, with one extra consideration:

Players in VR can lean inches from an NPC's face. Subtle artifacts (foot sliding, stiff shoulders, empty eyes) are far more visible than on a flat screen.

Use LookAt IK so NPCs track the player's HMD position for natural eye contact

VR Player Avatars: IK From 3 Points

The player has only 3 tracked points — headset + two controllers

void OnAnimatorIK(int layerIndex)
{
    // Hands follow VR controllers
    animator.SetIKPositionWeight(AvatarIKGoal.LeftHand, 1f);
    animator.SetIKRotationWeight(AvatarIKGoal.LeftHand, 1f);
    animator.SetIKPosition(AvatarIKGoal.LeftHand, leftController.position);
    animator.SetIKRotation(AvatarIKGoal.LeftHand, leftController.rotation);

    // (Repeat for right hand)

    // Head follows HMD
    animator.SetLookAtWeight(1f);
    animator.SetLookAtPosition(hmd.position + hmd.forward * 10f);
}

Limits of Built-In IK for VR

  • Only solves four end-effectors (hands + feet)
  • No spine estimation, shoulder prediction, or lower-body inference
  • Legs have to be faked — the player's legs aren't tracked at all

For production VR avatars, most developers use Final IK (VRIK) by RootMotion (~$90) — the industry standard, originally developed for Oculus's Dead and Buried

Controller-Driven Hand Animation

Standard pattern: a Blend Tree with two float parameters

public class VRHandAnimator : MonoBehaviour
{
    public InputActionReference gripAction;
    public InputActionReference triggerAction;
    private Animator animator;
    private static readonly int GripHash = Animator.StringToHash("Grip");
    private static readonly int TriggerHash = Animator.StringToHash("Trigger");

    void Awake() => animator = GetComponent<Animator>();

    void Update()
    {
        animator.SetFloat(GripHash, gripAction.action.ReadValue<float>());
        animator.SetFloat(TriggerHash, triggerAction.action.ReadValue<float>());
    }
}

The Animator uses a Direct Blend Tree with open hand, fist (grip), and pinch (trigger) motions

XR Hands: Optical Tracking

  • XR Hands package (com.unity.xr.hands) provides real-time optical hand tracking
  • Supported on Meta Quest 2 / 3 / Pro
  • Tracked joint data directly drives hand mesh deformation — no animation clips needed

This replaces controller-based hand animation entirely on hand-tracking-capable devices

Root Motion in VR: The Cardinal Rule

The virtual camera must always reflect the player's physical head position. No exceptions.

Three reasons root motion fails for VR players:

  • Tracking conflict — HMD is the authoritative source of position
  • Vestibular mismatch — virtual motion without physical motion = sickness
  • Responsiveness — you can't afford any lag between intent and movement

Unity 6.3 Specifics

Mecanim in Unity 6.3 is functionally identical to Unity 2022 LTS. Minor changes:

  • ResetControllerState (new) — resets Animator to initial state; useful for object pooling
  • 30% faster Legacy Animation evaluation (only matters if you use the old Animation component)
  • CreateStateMachineBehaviour is obsolete — use CreateNewStateMachineBehaviour
  • A completely new animation system was previewed at Unite 2024 — still in development as of April 2026

Key Takeaways

  • Clips are atomic motion; Blend Trees interpolate; Controllers orchestrate
